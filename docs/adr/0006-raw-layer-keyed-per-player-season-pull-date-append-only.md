# The raw landing layer is keyed per (player, season, pull-date) and is append-only

The raw layer stores verbatim `shotchartdetail` responses keyed per **(player, season, pull-date)**. The **pull unit is the season**, not the game. Completed seasons are **immutable single snapshots** (pulled once, ever). In-progress seasons accrue **dated snapshots** — re-pulls are written as new snapshots, never overwriting. Derived data recomputes from the latest snapshot.

**Why:** This corrects an earlier stated-but-wrong model ("each game pulled once ever"), which bolted a per-game promise onto a per-season endpoint — `shotchartdetail` has no per-game mode in v1. Append-only + dated snapshots preserve what the (unofficial, day-to-day-changeable) endpoint said on each pull date, which is exactly the value for a live season.

**Considered:** Decomposing the season response into per-game records to preserve a per-game write-once model — rejected: the endpoint hands back a season, per-game structure would be imposed by us for no v1 benefit. Per-game write-once returns legitimately in v2 for Case 3 play-by-play, where the endpoint *is* per-game.

**Consequences:** The key is designed for the future (the later in-progress-season demo needs no storage refactor), but the logic that consumes multiple snapshots — snapshot selection, re-pull scheduling, diff/merge — is *not* built in v1, where a completed season has exactly one snapshot. A future contributor must not reintroduce overwrite-in-place or a per-game pull unit for v1.

**Amendment (2026-07-23, v3 Phase 3) — live sessions extend the key with a time stamp.** The season loop pulls daily and may pull twice in a session (discovery, then frontier-anchored; retries within a day), so live-session snapshots are named `<pull-date>T<HHMMSS>[-role].json`. Append-only holds exactly as before — a retry writes a new stamp, never overwrites — and `T` sorts after `.` lexicographically, so stamped snapshots sort after the same day's plain `<pull-date>.json` and every "latest snapshot" glob stays correct unchanged. The stamps are the key working as designed, not clutter to clean up; each anchored artifact also records its `date_to`, per the raw-artifact self-description rule.

**Amendment (2026-09-25, the Jazz-first site plan) — the raw layer is mirrored off-machine.** The raw layer is the one thing everything else rebuilds from (the record store, every derived file, every deployed payload), and until now it lived only on the dev machine's disk (648 MB, gitignored). After every season-loop session, halted or not, the wrapper copies it to a private Cloudflare R2 bucket with `rclone copy --immutable`. Two flags carry this ADR's semantics into the copy: `copy`, never `sync`, so a local loss or corruption can never propagate into the backup, and `--immutable`, so an existing object that differs from its local file is an error to investigate, never an overwrite; append-only on disk stays append-only off it. The layer's key, pull unit, and local-only acquisition are unchanged, and the backup is never a read source for any derive or load. The credentials live in rclone's own config, never in the repo, and the bucket stays private because the NBA's data stays the NBA's.

# The team shot payload is a fifth contract with the team as subject

The Jazz surface reads a **team shot payload** (`public/data/_teams/<tricode>/<season>.json`), a fifth typed contract beside the four hero contracts, with its own schema version, golden, and load boundary. Its source is one team-wide `shotchartdetail` pull (team ID set, player ID zero, `FGA` context measure), which returns every shot every player took for that team in the season together with the `LeagueAverages` frame. The payload persists the enriched shot row the hero contract already defines **plus `playerId` and `playerName` per row**, the rolled-up zone baseline in the existing shape, the observed **roster** from the same session's `commonteamroster` snapshot, and team metadata in `_meta` (team identity, frontier fields, source snapshots, conflict count). It has no usage field: usage is a player fact, and ADR-0069 forbids computing one.

**Why a fifth contract and not a hero payload with a team's name in it.** The hero schema's `_meta` is a player's record (player ID, usage, the Advanced-artifact oracle) and would have to lie or go null. The team payload is also read differently: sliced by player for the roster rail and by game for the ledger, so player identity per row is load-bearing, and the pre-drop row count per player per game is what its oracle reconciles. Reusing the enriched shot row keeps `aggregateShotMetrics` the only implementation of selection and making math (ADR-0009): the team profile is one call over all rows, a player profile one call over that player's rows, a game row one call over that game's rows.

**Oracles, at load and again at export (ADR-0080's discipline).** For every game in the payload, every shooter's pre-drop row count equals that player's field-goal attempts in the game's `BoxScoreTraditionalV3` line, and every box line with attempts has a shooter. The team's game total follows. The box pair is therefore a hard requirement for every game the payload contains, which is also what defines the frontier. Frontier fields are computed from the rows and verified at the load boundary as the hero contract does. Zone-point conflicts are dropped and counted (ADR-0019). Row order is **chronological** (game date, game, period, clock, event), a defined order rather than the response's, because the payload has no single-player response order to preserve and the ledger reads it by game.

**Storage.** Team shot rows load into the existing `shot` table at natural identity: a shot is a shot, and a Jazz hero's rows arrive from both his pull and the team pull and must agree (change detection arbitrates; a disagreement is a contradiction). The team loader leaves an existing row's response ordinal untouched so the hero exports' byte parity is unaffected. The roster loads into `roster_entry`, observed nightly, current state only, with a scope-complete flush so a departed player leaves the roster and keeps his rows.

**Consequences.** `golden:regen` gains a fifth pair, produced by a file derive over a truncated team snapshot plus its game's box line, and the record-store path is held to byte parity with it. A team sync copies the team payload beside its future siblings; the app-side real-data guard asserts frontier equality across the team payloads. A future contributor must not add a team usage or any computed team rate to `_meta`, must not order rows by response position, and must not admit a game without its box pair.

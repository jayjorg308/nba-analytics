# Postgres is the system of record behind the committed JSON export

Storage moves from JSON files all the way down to a relational record: a Neon-hosted Postgres becomes the system of record and compute substrate, and the committed `public/data/` payloads become an export from it. The database sits *behind* the deployed layer, never in front of it — the app stays a static site reading committed JSON, because the committed payloads are load-bearing four ways: the guards assert frozen verdicts against them on every clean clone; the publish unit is a reviewable, revertable data commit (ADR-0057) whose gate-on-green discipline would otherwise have to be rebuilt as staging/promotion machinery; static files serve from a CDN with no API, no secrets, and no outage story for data that changes at most daily and is identical for every visitor; and any historical page state reproduces from a git ref. A live query path is deferred until some surface needs queries that cannot be enumerated at export time (a league-wide comparison tool would; game-by-game reports for registered heroes and split-date free-throw windows do not), and it would then front only that surface. The raw layer keeps its job (ADR-0006): append-only verbatim snapshots remain the ultimate rebuild source, which is what makes trusting a hosted free tier acceptable — the database is rebuildable, so losing it is an inconvenience, never a loss. Repo bloat stays bounded because the repo commits only what the product renders (~1.5 MB per hero-season across the four contracts); league-scale data lives only in the database.

The schema stores observations and computes derivations. Observed tables: `shot` (including zone-point-conflict and Backcourt rows — stored as observed, dropped-and-counted at export per ADR-0019), `pbp_event` (game-owned and shared per ADR-0045; chosen over loading only classified outputs so the database holds the observation its most rule-laden derivations cite, and so league-wide trip reconstruction is a query rather than a thousand files), `game` (with source-observed home/visitor abbreviations; the ADR-0028 static team map becomes a derivation over them), `player`, `team`, `creation_split` and `league_zone_baseline` (observations *at aggregate grain* — the tracking dashboards and the LeagueAverages frame are their own record systems, never derivable from stored shots), `player_season` (sourced facts only, e.g. the ADR-0069 usage rate), and the oracle artifacts (league season totals, box-score lines) that the FGA oracle and Gate 5 reconcile against. `ft_trip` and the assist/event-match statuses are *derived* tables, rebuilt per run and stamped with their run; a trip's identity is its causing foul event, not (game, period, clock), because clock ties are physically possible and the causing event is how trips classify. Every other derivation is a SQL view or stays in the TypeScript aggregation — no derived-metric tables; a materialized view is permitted later only as explicit cache for a demonstrably slow analysis query, never as record. There is deliberately no `zone` table: the NBA zone vocabularies are CHECK constraints on `shot`, and evaluation grain, zone-to-points, and every rollup stay in code, so retuning a product grain remains an aggregation change, never a data migration — and point value stays observed (the scorer's SHOT_TYPE), never computed from zone, or zone-point conflicts would become unrepresentable. Keys are natural NBA identity throughout (`player_id`, `team_id`, `game_id`, `(game_id, game_event_id)`), no surrogates, because every cross-source reconciliation in this repo joins on NBA identity exactly (ADR-0036). The database is product-blind: no slugs, heroes, canonical seasons, verdicts, or claim thresholds — the export step joins the database to the hero registry, keeping product judgment in git where the guards see it and the database reusable for players who will never be heroes.

Versioning is current state only, with lineage pointers. Observed loads are upserts by natural key with change detection (each run reports inserted / unchanged / changed; a changed row at or inside a published frontier is a contradiction and halts for a human, the season loop's existing grammar) — no bitemporal rows, because the raw layer already *is* the history and versioning normalized copies would duplicate that job with a less faithful copy. Lineage is a snapshot catalog (the files on disk stay the artifacts) plus one `load_run` row per execution, with run/snapshot provenance on rows. Row-grade facts are database constraints; the cross-source reconciliation identities (the FGA oracle, Gate 5's per-game and season-total equalities, four-way frontier agreement, tracking-shortfall arithmetic and its negative-shortfall hard-fail) remain hard-fail pipeline checks in Python, run at load and again at export — they are per-run coherence assertions *between sources*, trigger-based enforcement would make staged loads impossible to even attempt, and halt-for-a-human belongs in the loop's reporting, not a constraint violation string.

**Amendment (2026-08-24, living-season provenance).** A living season's daily loads broke two assumptions the completed-season slices could afford. First, *which snapshot a payload names* is not derivable from row provenance (unchanged rows keep their first-asserted snapshot, so a scope's rows legitimately mix) nor from the catalog's latest path (the replay proof keeps partial frontier-anchored artifacts whose T-stamped names sort after the real full-season pulls — "latest file" is a landmine). It is therefore recorded explicitly: every load writes a `source_head` row per scope — "this scope's current state equals snapshot X" — in the same transaction as the rows, and exports read heads, never row provenance. The head is correct by construction because loads assert their scope *completely*: change detection plus deletion detection guarantee current state equals the head snapshot's content, and a deliberate load of an older snapshot moves state and head together, coherently. Row provenance stays first-asserted lineage, deliberately. Second, change detection gained classes: a scope-complete flush reports existing rows absent from the incoming snapshot as **deleted** (a vanished observation is a contradiction; halts like changed), and cumulative aggregate tables declare **monotone columns** (counts that legitimately grow daily — creation splits, league baselines, season totals; usage's rate column is free) so a changed row whose diffs are confined to non-decreasing monotone columns and free columns classifies as **grown** and flows without halting, while any decrease or event-row edit still halts for a human. `shot.source_row` is a free column: a cumulative re-pull may reorder the feed without any shot changing, and the payload order follows the reigning snapshot; a real content change on a shot still halts. This replaces the interim all-changes-halt behavior and is what makes daily loads of a growing season routine while corrections stay loud.

Validation and sequencing: the migration lands against a byte-identical parity oracle — the export, over the fully loaded database, must reproduce every committed payload exactly, with no contract, golden, or guard change in the same PR (provenance fields included: they are loaded facts, not exclusions). Contract evolution — the date-grained free-throw payload ADR-0079 waits on, game-by-game report payloads — comes in separate PRs after parity is proven, each moving schema + derive + golden together per the existing rule. The golden handshake survives by running the real loader→constraints→export path against an ephemeral Dockerized Postgres per pytest run (which strengthens it: a constraint that would reject real data now fails a golden test); vitest and the deployed-data guards stay database-free. Completed seasons migrate first, behind the parity oracle, with zero operational risk; the season loop is rewired last, gated on rerunning the replay proof over the DB-backed loop against Cody 2025-26 and holding it to the same oracles — with a decision date of about October 1, 2026: if the proof has not passed, Ace Bailey's 2026-27 activates on the file-based loop and the switchover finishes during the dark phase, where nothing publishes. The daily loop's new dependency on Neon reachability is accepted as a loud halt and next-day resume, the loop's existing failure mode. **Cutover executed 2026-08-24**, six weeks ahead of the decision date: the DB-engine replay proof passed every oracle on its first run (frontier exactness and gate truth on all six calendar days, the flip signal on exactly the boundary day, all four terminal frames byte-equal modulo provenance, the scratch store living the season's lifecycle from empty), and the loop's default engine flipped to the record store; `--engine files` remains the fallback.

**Amendment (2026-10-22, the league frame is accepted, and recorded, in the loop).** The morning after 2026-27's opening night the team session halted on `league_zone_baseline`: overnight the NBA moved one missed shot from In The Paint (Non-RA), Center, Less Than 8 ft (304 to 303) to Left Corner 3 (124 to 125), the league total unchanged. Scorers correct shot locations after games routinely, and a second path shrinks the frame too: every session anchors the frame at its own frontier, and the table holds one current frame per season, so a hero session whose tracking lags behind the team session's frontier would replace a later frame with an earlier one. Under the all-decreases-halt rule either would stop a session most mornings. The frame is the league's aggregate, not an observation of the subject, and each game is priced against its own pre-game ruler (ADR-0089, a separate table where a changed ruler still halts), so the season loop's loads (`load_hero_season` and `load_team_season` with `accept_frame_changes`) now apply league frame changes without halting and record them: the session's status file gains `leagueFrameChanges` (the incoming frame's through-date and snapshot, and every cell that shrank), and the session's report lines and data commit say how many. A record with the same through-date as the previous session's frame is an NBA correction; an earlier one is a session trailing another's frontier. Everything else keeps the amended rule above: a subject correction (a shot, a box line, the player's season facts) still halts for a human, and the command-line loaders keep halting on frame changes too.

**Amendment (2026-10-28, player renames, and a frontier the store has passed).** The first hero loads of 2026-27 met two more ways a living season contradicts the store with nothing wrong. First, stats.nba.com renames people: between July and October its league endpoints changed 'Terrence Shannon Jr.' to 'Terrence Shannon Jr' and 'Moussa Cisse' to 'Moussa Cissé'. The hero load restages every league player's name from the season's Advanced artifact, and the `player` table keeps one name per person, so from 2026-10-27 every hero session halted on two players who play for no hero's team. A name is an attribute of the person, not an observation of the subject, so the season loop's hero loads (`load_hero_season` with `accept_frame_changes`) apply renames without halting, under the league frame's rule: the session's status file gains `playerRenames` (each rename as the load reports it), and the session's report lines and data commit say how many. The command-line loader keeps halting. Two consequences are accepted. Exports look a hero up by name, so a rename of a hero still fails loudly at export. A published game payload is immutable, so a rename of a player in a published game surfaces as the team session's refusal to rewrite it, a reviewed `--allow-rewrite` decision rather than a silent change. Second, the team session (ADR-0082) loads every shooter on its roster into the shared `shot` table through its own frontier, while a hero session follows tracking, which can trail the previous night's game. On 2026-10-27 the game-night load had written game 0022600126 (2026-10-26) the night before; tracking reached only 2026-10-25, the frontier retreated, and the hero load, which asserts every one of the hero's season shots, read his game-126 rows as deletions. Bounding only the load's scope to the frontier would not do: the tracking load, the corpus rebuild, and the four hero exports also read every season shot of the hero, so the later rows would enter payloads anchored earlier. The hero session therefore defers when the store already holds the hero's shots in a game after its settled frontier (`store_shots_after`, checked before the anchored pulls), the loop's standing rule that tracking lag defers, and the first session after tracking catches up loads them. In the usual case the deferral costs nothing: a frontier retreated past one game is the frontier the previous session already derived.

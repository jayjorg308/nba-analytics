# Game cards are a fifth committed contract over a mechanical roster

Game cards ship as site pages in the tool class, not as share images and not behind an API. A card is one player's night as priced facts at `/game/<player-slug>/<date>` (the season-permalink ordering; `game` joins the reserved-route guard): expected points from his diet — his attempts priced at the season's league zone rates — over points actually scored and their difference as conversion, with THE CREDIT and THE LINE as chips and a drill-in receipt itemizing every attempt and trip down to the box total (the poster + receipt composite chosen by a three-variant throwaway prototype, the ADR-0078 method; verdict captured in the prototype's NOTES.md before deletion). A tool, not an argument (ADR-0076's stance): computed numbers and structural copy only, no verdict, no grades, no authored prose, so no verdict-guard obligations — and deliberately no per-game ability claim anywhere: selection is priced (his choices at league rates, honest at any sample size), conversion is what happened, and nothing estimates a rate, which is why cards carry no small-sample flag. Creation never appears at game grain (ADR-0033's boundary). The honesty rails are the house patterns at game grain: heaves and zone-point conflicts struck in the receipt, unpriced, counted when nonzero (ADR-0019); unknown makes surfaced in the CREDIT chip, never hidden; technical free throws as their own receipt line whenever nonzero so the receipt always sums to the box line; "scoring attempt" stays reserved; structural copy stays adjective-free with one stance sentence per card held to the structural-copy verification discipline. Discovery follows the compare pattern: a `/game` landing with a roster picker linked from the directory, prev/next-game links on the card, a hero-page link when the player is registered, hero pages themselves untouched (a game-log strip there is a separately-judged later addition).

Membership is mechanical, never curated: the **card roster** is every player at or above a season FGA bar — 300, one named constant with rationale, moved only by PR (~284 players in 2025-26) — plus every registered hero regardless. The bar is a product-membership rule, not a data-cost rule, because the acquisition cost is roster-size-insensitive: any interesting roster spans all 30 teams, so CREDIT and LINE require effectively the full season corpus (~1,230 game pairs) either way — the same corpus the exact-trips research needs, so the cost is shared. v1 is the completed 2025-26 season only. Live 2026-27 cards are explicitly deferred past Ace Bailey's flip: they require league-wide shot-pull tooling (per-player nightly pulls do not scale to 284 players; zones must come from `shotchartdetail`, never derived from coordinates — ADR-0012's line) and a roster-crossing rule, and they will not share a maiden season with the loop's first live campaign.

The data is **contract five: the game-log payload** — one compact committed file per roster player-season (per game: date, opponent, home, a box-line subset, shots as zone/value/made/period/assistStatus, trips, the technical free-throw count) with the season's league zone-PPS table embedded so each file is self-contained, the house pattern of every payload carrying its baseline. Rejected alternatives: reusing the existing contracts for the roster (~200MB committed — the shot payload carries coordinates and grains a card never reads) and the API path (Neon is reachable from Vercel, but a serverless read layer would be the site's first runtime backend — secrets, cold starts, guards that can no longer assert against committed data — and ADR-0080 reserves that step for a genuinely non-enumerable surface, which 284 players × their games is not; ~20MB committed, one-time for a completed season, keeps static CDN serving, publish-as-commit, and URL reproducibility). Heroes read this same contract rather than computing cards from their three siblings client-side, so the page has one load path and registry membership stays a product fact, not a data shape. The contract is the first born DB-native — no file derive exists — so its golden pair runs the record-store pattern: pytest loads truncated fixtures into an ephemeral Docker Postgres, runs the real export, and compares byte-for-byte, with its own regeneration script; vitest strict-parses the golden. The export hard-fails on the per-game receipt identity against `box_score_line` (priced + unpriced field-goal points + trip FTM + technical FTM must equal box points, every game) and on the season FGA oracle; deployed guards re-assert strict parse, the receipt identity, and the roster bar over committed files; and for registered heroes the games file must agree at game grain with all three deployed siblings — shots with the shot payload, assist statuses with the context payload, trips with the freethrow payload — so the fifth contract can never silently drift from the four.

Rollout is heroes-first: contract, export, goldens, guards, landing, and page ship on the eleven registered heroes, whose store data is already complete, with the prototype rewritten properly (never promoted) and deleted; the mass import then proceeds as resumable batches (~284 `shotchartdetail` pulls plus ~1,540 missing corpus pairs, the skip-existing discipline of ADR-0066), each batch ending in an export tranche and a data commit so the roster grows visibly; and the completed import closes with the spectrum analysis — best and worst shot diet, best and worst conversion against diet, league-wide at the roster bar — delivered as a report, not a product surface.

# A team session publishes each new game with its card

The season loop's team session publishes a report card for every game newly inside its frontier, in the session that first sees the game final: on a game night the 23:45 window, otherwise the 06:30 run. For each paired game through the candidate frontier that has no published game file, the session puts on disk what the file will name, pulling only what is missing: the pre-game ruler (the league frame through the day before, ADR-0089), both teams' one-day pulls (the teams read from the game's box score, ADR-0036's exact-identity rule), and a league game log that names the game. It loads them, exports the game files and the season index (ADR-0088) into `data/derived/_teams/<tricode>/<season>/games/<session>/`, and in live mode syncs them with the team shot payload and the ledger, draws the cards of every published game that lacks one (`npm run cards:games -- --missing`), runs the full gate, and lands one data commit. Dark mode sources, loads, and exports the same way and publishes nothing. **Amends ADR-0057 and ADR-0088.**

**The data commit admits the cards its own games need.** ADR-0057 limits the automated commit to deployed payloads and their freshness metadata. A report card that publishes without its share image is a link that previews as the site's generic card, and a card drawn the next day by hand is the freshness ADR-0057 exists to remove. So the team data commit also carries the share cards under `public/social-cards/<team>/`, on three conditions that keep it a data commit: the image is drawn by committed code (`scripts/generate-game-cards.ts`, `scripts/generate_game_cards.py`) from that commit's game files and committed assets only (the wordmark, the pinned faces); the loop only adds cards, never redraws one, so a shared card stays what it was; and hero cards, which sit at the top of `public/social-cards/` and carry authored judgment, never ride it. When the computed copy's words change (ADR-0090, to be recorded), redrawing every card is a human rerun in a PR.

**Readiness joins the frontier, and lag defers.** A game is ready when its one-day pulls each hold that game alone with as many rows as the side's box FGA, and the league game log names it. A pull on disk that falls short is pulled again; one that still falls short, or a log that still lacks the game, is lag, never failure (ADR-0058): the game waits, and because a frontier is a whole date, the frontier stops at the last date before it. The anchored team pull and the team payload then stand at that date too, so the team payload, the index, and the game files always publish at one frontier. A contradiction still halts: a shooter whose rows disagree with his box line at load, a ruler missing a zone, a published game whose bytes would change.

**The subject reads its own one-day pull.** ADR-0088 sourced the subject's side from the team's season pull, which the session already makes. Wiring the loop showed that cannot hold: each session's season pull becomes the source head the export names, so a game file written tonight would name a different snapshot tomorrow morning and refuse as a change. An immutable file must name a source that never moves, so the subject's side, like the opponent's, comes from a one-day pull of the game, one more call per game. The export already preferred a side's one-day pull when one was loaded, so how it names a side's source is unchanged; a test pins the moving head and the stable file. The committed 2025-26 files, exported from one scratch load, name the season pull and stay as they are.

**Immutability is checked against what is published.** The export compares every game with its published file, not with its own output directory: identical bytes stay put and are not exported again, a game with no published file is written, and a published game whose bytes would change halts the session (a correction travels by PR, `--allow-rewrite`). `team:sync` is the backstop. It copies the team shot payload, the ledger, and the game export from one session only, and fails before copying anything when one of the three is missing, when they come from different sessions, when an index row has no game file, or when a published game file would change.

**Guarded from the first game.** The registry gains a season by config change once that season's first payloads deploy, so the first data commits of a season land before the registry lists it. The deployed-pair guards and the card generator therefore read the published seasons from disk (`src/teams/published.ts`), not from the registry, and a data commit is checked by the full gate from its first game. The emitted share pages stay registry-scoped, because the app routes only registered seasons.

**Consequences.** Opening night needs one human step after the first data commit: the registry PR that adds 2026-27 and makes it canonical, after which every game's card appears with no manual step. Game publishing reads the record store, so a live team session on `--engine files` halts before its first pull. A game on the league's own opening night has an empty ruler and prices against the prior season (ADR-0089), which needs the prior season's game log loaded; the export halts and says so if it is not. A future contributor must not let the loop redraw or delete a published card, must not let the subject's side name the season pull, and must not publish a game file whose sources are not on disk in the raw layer.

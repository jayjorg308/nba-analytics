# Per-hero share pages are emitted at build time over generated marquee cards

Sharing a hero page now previews that hero. Two mechanical layers deliver it: **generated cards** — `npm run cards:generate` renders one committed 1200×630 card per registered hero (`public/social-cards/<slug>.png`) — and **emitted share pages** — `npm run build`'s final step (`scripts/emit-hero-pages.ts`) writes `dist/<slug>/index.html` and `dist/<slug>/<season>/index.html` for every season argument: copies of the built `index.html` with the share meta swapped (title, description, the `og:`/`twitter:` pairs) plus a per-page `og:url`. Vercel serves real files before applying the SPA rewrite, so a scraper reads hero meta at every hero route while the app still boots and resolves the hero at runtime exactly as before — ADR-0022's model stands untouched; this layer only changes what a non-JS reader sees.

**Why build-time emission, not an edge function or prerenderer:** the deployment is deliberately static (ADR-0010/0022) — committed payloads fetched by a static app. An edge meta-injector would add a runtime dependency and a second copy of routing truth; a prerenderer would add a headless browser to the build for what is a string transform. Emission is deterministic, runs from the same node-safe registry every other tool reads (registering a hero is what publishes its share page, the index-tile rule again), and is testable as a pure function: `src/heroes/socialCards.ts` is unit-tested against the REAL `index.html`, so a meta-block refactor fails the suite before it can ship stale share meta, and the emit step hard-fails on a missing pattern or a missing card (the partial-sync stance, applied to share assets).

**The card is the marquee.** No new art direction per hero: the card renders the directory's poster grammar (ADR-0065) at og:image size — the radial-glow ground and B&W treatment reproduced from the CSS, the headshot cutout grounded bottom-right, the derived meta eyebrow (`indexMetaOf`, never authored twice) over the display-face name over the verdict cue, the wordmark as signature. Every input is already committed (headshot, wordmark) or already registry copy. Fonts are the pinned @fontsource files themselves (ADR-0020): WOFF v1 is a zlib-wrapped SFNT, so the generator unpacks the shipped webfonts with the stdlib rather than re-downloading a cousin that could drift; the cue's `→` is drawn as strokes because the latin subset carries no U+2192. One card per hero, shared by its seasons — the card names the player, the page meta names the season.

**`og:url` becomes correct exactly here.** The product-wide card (ROADMAP, Launch item 1) deliberately omitted `og:url` because scrapers treat it as canonical and a root value would collapse a shared hero link back to the front page. Per-page emission is the condition under which it stops being a hazard: each emitted page carries its own canonical (`/<slug>` for the alias, `/<slug>/<season>` for permalinks). The root `index.html` keeps the product-wide card and still no `og:url`.

**Amendment (2026-07-28) — emitted pages also preload their payloads.** Each emitted hero page now carries `<link rel="preload" as="fetch" crossorigin>` for exactly the payloads its app boot will fetch: the four required siblings, plus the prior argued season's shot payload when the page is the canonical season with a growth coda (ADR-0061's exact fetch set, encoded in `payloadPreloadPaths`). Before this, the fetch waterfall was HTML → bundle → React boots → then the payload requests — the data didn't start downloading until the app was already running, which was most of the visible loading beat on a warm cache. Preloading from the emitted HTML starts the downloads at parse time, in parallel with the bundle. The `crossorigin` attribute is load-bearing: `as="fetch"` must match `fetch()`'s default credentials mode or the browser downloads everything twice and warns. The root index.html stays preload-free (the directory fetches no payloads), and the emit step remains the only consumer — runtime hero resolution (ADR-0022) is untouched.

**Consequences:** the add recipe's share assets are mechanical — `hero:add` generates the new hero's card right after the headshot (both are formula assets, ADR-0063's boundary honored: nothing on the card is judgment). One authored input does reach the card: the eyebrow derives from the kicker, so the generator SKIPS any hero whose kicker still carries the scaffold sentinel — sentinel text never bakes into a PNG — and the committed-card guard holds the suite red until the kicker is authored and `cards:generate` reruns (the hero:add checklist names that step). A registered hero without a committed card is a red suite (`socialCards.test.ts` asserts existence and exact 1200×630 per hero) and a failed build. Changing the card design means changing the generator and regenerating every card in one PR — cards never drift apart per hero. The cue and eyebrow on the card are structural copy; the card carries no verdict language, so it creates no new guard obligations.
